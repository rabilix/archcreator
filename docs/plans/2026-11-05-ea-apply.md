# Plan: write the as-built architecture into a copy of the EA model (`ea-apply`)

Status: revised after two review rounds (Codex, 2026-11-05: 10 + 4 findings, all taken over; section 13). Branch `feature/ea-apply`
(from `develop`).

## 1. Goal

The user gives a C module (or folder) and an Enterprise Architect 16 model (`.qea` / `.qeax`). archcreator already
recovers the module's as-built architecture from the code (`model.json`) and can export it as XMI. Missing is the step
the user does by hand today: getting that architecture into the EA model so it can be reviewed there.

`archcreator ea-apply` writes the as-built architecture of one analysed module **into a copy** of the EA model, through
EA's own Automation Interface (COM), so EA keeps its tables consistent. The user opens the copy in EA and reviews it,
alone or together with the agent.

Decisions this plan rests on (2026-11-05, user):

- Delivery: the tool writes a **copy** of the model; the original is never written.
- No third-party EA MCP server: archcreator drives EA's Automation Interface itself (concept-only; nothing copied
  from any other product, no product named in code or commits).
- Content is chosen per run: static structure, data/signal flow, behaviour, trace to code.
- Target: EA 16 on Windows (EA 16.0 build 1605 answered COM in `tools/ea_verify.py`, 2026-10-21).

## 2. Principle change (approved by the user, 2026-11-05)

README today: "archcreator never writes `.qea`/`.eap` files." New rule:

> archcreator writes an EA model only through EA's Automation Interface, only into a copy it made itself or the user
> named, never into a protected model (section 5), and never deletes anything.

`analyze`, `scan` and the design comparison stay read-only. Only `ea-apply` writes, and only the copy.

## 4. Command

```
archcreator ea-apply --repo <target repo> --in <analyze output folder> --model <copy.qea|copy.qeax>
                     [--from <model to copy>] [--content structure[,trace]] [--profile P | --profiles-dir D]
                     [--design <qea>] [--dry-run] [--timeout <s>] [--json]
```

- `--repo` and the profile options as for `analyze`: `ea-apply` resolves the protected models itself (section 5)
  instead of trusting what an output folder says. `--in` must be an `analyze` output of a module of this repository:
  `manifest.json` `target_commit` must equal the repository's current commit, else exit 2 ("analyse again").
  A dirty working tree (in the manifest's `target_dirty` or now) is refused too, because the same commit can then
  mean other code; `--allow-dirty` accepts it, and the run tag `target_dirty = true` on the component says so.
- `--model`: the copy to write; extension `.qea` or `.qeax`.
- `--from`: make `--model` as a copy of this model first (section 6). With `--from`, `--model` must not exist; it is
  created exclusively. Without `--from`, `--model` must exist and must not be protected.
- `--content`: `structure` (always) and optionally `trace` (default: both). `signals`, `behaviour`, `ports` are refused
  in increment 1 with exit 2 naming the increment that brings them.
- The as-built root: package `archcreator (as-built)` at the model root, created when missing; below it
  `<Module> (as-built)` with `BlackBox`, `Interfaces`, `Context/<Other>`. Nothing is written outside this root.
- `--dry-run`: guard, copy check, identity read and plan, write `plan.json` and `job.json`, start no EA. Every OS.
- Output folder `<in>/ea_apply/`: `plan.json` (canonical, byte-stable for the same model and copy state), `job.json`,
  `apply_log.json` (per operation: created / updated / unchanged / failed, EA's message), `apply_summary.json` (schema
  `archcreator.ea_apply/1`: exit code, model path, counts, error). `--json` prints the summary.

Exit codes: 0 applied; 2 usage or guard; 5 internal error; **6 (new) EA automation failed** (EA did not start or open
the copy, an operation failed, timeout). On 6 the copy may be partly written; a re-run continues it (section 7), and
the log says which operations ran. Front ends must learn 6 (flexcli, increment 1b).

## 5. Guard: the protected models

Protected are: the profile's `design.model` resolved against `--repo`; `--design` when given; `--from`; and every
`.qea`/`.qeax`/`.eap`/`.eapx` file inside `--repo` (a project's model lives in the repository; the copy does not).

`--model` is refused (exit 2) when:

1. it is inside `--repo` or inside the output folder of archcreator's own results;
2. it has the same file identity as a protected model: `os.path.samefile` (device + inode / volume serial + file index,
   so hard links, symlinks, junctions and case differences are all caught), checked for every protected model that
   exists;
3. it is read-only, or (without `--from`) it does not exist, or (with `--from`) it exists;
4. it is not an EA model: opened read-only with SQLite it lacks `t_object`, `t_package`, `t_connector`, `t_diagram`.

The driver repeats the identity check right before `OpenFile`: the job carries the protected paths, the driver compares
the file id of the target with each (`fsutil file queryFileID`) and refuses on a match or when a protected file id
cannot be read. Python checks again after the driver exits that every protected model's size and modification time
are unchanged (a tripwire, logged).

## 6. Making the copy

`--from` copies with SQLite's online backup (`sqlite3.Connection.backup` from the source opened read-only), which
includes committed WAL content and never reads a half-written page. Before that, the source must not be open in EA:
when `<source>-wal` or `<source>-shm` exists, or SQLite reports the database locked, exit 2 ("close the model in EA").
The new file is created exclusively (`open(..., "xb")` then backup into it), then checked as in section 5 rule 4 and
with `PRAGMA integrity_check`.

## 7. Identity and re-runs

COM cannot set `ElementGUID` / `ConnectorGUID` (read-only), so identity is a tagged value.

- `xmi.build()` exposes the key of every object it creates (today the key is only hashed into the id). Each element,
  package and connector `ea-apply` creates gets the tag `archcreator_id` = that key and `archcreator_module` = the
  target module id. Packages carry their tags on `Package.Element`. Features (the one operation or attribute of an
  interface) are identified by their owner's key plus the feature kind; the interface owns exactly one.
- Before the driver starts, Python reads the copy read-only with SQLite (`t_objectproperties`, `t_connectortag`,
  `t_object`, `t_package`, `t_connector`) and finds every object with an `archcreator_id`, **anywhere in the model**,
  with its `ea_guid`. Then:
  - two objects with the same `archcreator_id`: exit 2 with both locations (the user resolves it);
  - an owned object moved by a person **within** the as-built root of this module: updated where it is, not moved
    back; logged `moved`;
  - an owned object found **outside** that root: exit 2 with its location; nothing is written outside the root;
  - not found: `create` operation; found with other fields: `update` by GUID (`GetElementByGuid`,
    `GetConnectorByGuid`, `GetPackageByGuid`); same fields: no operation.
- The plan is computed from what the copy contains now, so a run that failed half way is continued by the next run.
- Owned fields `ea-apply` may change: name, stereotype, notes, the tags it writes, a feature's name. Anything else
  (position, colour, a person's own tags, connectors or elements without `archcreator_id`) is never touched.
- Stale (in the copy, no longer in the plan): never deleted in increment 1. Stale elements and connectors **stay as
  history and are marked**: tag `archcreator_stale` = commit of the run, stereotype replaced by `stale` (the old one
  kept in the tag `archcreator_stereotype`), name suffix ` [stale]`. So the copy is "the current as-built structure plus
  marked history", never presented as current only: the summary counts current and stale separately and lists every
  stale object. A stale object that is planned again gets its stereotype and name back and loses the tag (revival).
  Removing stale objects (`--prune-stale`, owned objects inside the root only) is a decision for increment 1b.

## 8. Trace switch

What `trace` adds, exactly; without it these fields are empty or absent, everything else is identical:

| Object | Field with `trace` |
|---|---|
| Component `<Module>` | notes: the module's files |
| context Component | notes: its files |
| provided Interface | notes: `defined at …`, `declared in …` |
| Usage | notes: one evidence line per use; tags `first_evidence`, `via_macros` |
| Dependency «as-built» | notes: one line per symbol with its use count |

`evidence_count`, `kinds`, `usr`, `module_id`, `signal` and the run tags stay without `trace`: they are structure.
The XMI export always uses the full mapping; its bytes do not change (section 11, golden file).

## 9. How EA is driven

As in `tools/ea_verify.py`: `powershell -NoProfile -NonInteractive -ExecutionPolicy Bypass -File driver.ps1 -Job job.json`;
`EA.App`, `Repository.OpenFile(copy)`, operations in order, one JSON line per operation, `CloseFile()`, `Exit()`.

- `driver.ps1` is a fixed file in the package (`src/archcreator/ea/driver.ps1`). The job is data only; the driver
  dispatches a closed set: `ensure_package`, `ensure_element`, `ensure_feature`, `ensure_connector`, `set_tags`,
  `mark_stale`, `unmark_stale` (1b: `ensure_diagram`, `place_on_diagram`). It never calls `Invoke-Expression`,
  `Repository.Execute`, `SQLQuery`-writes, any `Delete*` method, or a script/add-in.
- Connector types are those the probe (increment 0) shows EA stores: the job uses EA's names (`Realisation`, `Usage`,
  `Dependency`); a type the probe did not confirm is not used.
- EA must not be running when a run starts: any `EA.exe` process → exit 2 ("close Enterprise Architect"), so a
  person's open session is never touched.
- Timeout per run (`--timeout`, default 900 s: EA's licence check can take minutes, EA_VERIFY.md). On timeout only an
  EA process that is provably this run's COM server is ended: started after the driver, and its command line carries
  the COM launch switch (`-Embedding` / `/Embedding`), which an EA a person starts by hand does not. Any other EA
  process is left running and the summary says so. Exit 6. The process logic moves from `tools/ea_verify.py` to
  `src/archcreator/ea/session.py`, and the tool imports it.
- Not Windows: exit 2 unless `--dry-run`.

## 11. Tests

Offline (every OS):

- **Golden XMI first**: before any change to `xmi.py`, the XMI of fx01 `alpha` (context all), and of the signal and
  macro fixtures used in `test_xmi.py`, are stored under `tests/fixtures/golden/`; afterwards the export must equal them
  byte for byte.
- `build()` keys: unique, stable across runs, every XMI id equals the hash of its key.
- `guard.py`: refuses the design model by same path, other case, symlink, hard link; a model inside `--repo`; an
  existing target with `--from`; a missing one without; read-only; not an EA model; unknown content.
- `copy.py`: copy of a closed fixture model equals it table by table; refused with a `-wal` sidecar and while another
  connection holds a write lock.
- `identity.py` + `plan.py` on fixture copies: empty copy → only creates; copy after a simulated apply → no
  operations; a changed note → one update; a duplicate id → exit 2; a moved object inside the root → update in place; outside the root → exit 2; a dropped
  dependency → stale; revival → unstale; trace off → section 8 fields empty; order (no connector before its ends,
  no element before its package); byte-stable `plan.json`.
- `apply.py` with a fake driver: created / updated / unchanged / failed lines → log and summary; exit 6 on a failed
  operation and on timeout; tripwire on a changed protected model; dry run writes plan and job only.
- `driver.ps1` static: only the closed operation set; none of the forbidden calls of section 9.
- CLI: `ea-apply` without `--dry-run` on non-Windows → exit 2; commit mismatch → exit 2; dirty tree → exit 2,
  with `--allow-dirty` → applied and tagged.
- `session.py` with fake process lists: EA running at start → exit 2; on timeout only a new process with the COM
  launch switch is ended, a new one without it is left and reported.

Live (Windows with EA 16, by the user): `ea_probe.py --go`, then `ea_verify.py apply --go`: first apply; read the
copy back and assert per object type, name, stereotype, ends, feature, owned tags and notes against `plan.json`;
second apply → no operations; a person's element and a moved element untouched / updated in place; a dropped
dependency stale, then revived; a run killed half way, then completed by the next run.

## 12. Risks

- EA licence dialog or network check blocks COM: long default timeout, process cleanup, exit 6 with the reason.
- COM is slow per call: one driver process per run; existing objects found offline with SQLite; writes only for
  differences.
- EA stores other names or ignores fields: increment 0 probe before increment 1 relies on them; live field checks.
- Writing the wrong file: section 5 in Python and in the driver, exclusive copy, tripwire, no delete.
