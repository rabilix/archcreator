UML vs code: four App modules

BMW PCU48 (100554). Compares how DCDC_FSM, DCDC_Safety_Functions, Error_Check and SEV are described in the Enterprise Architect model 100554_BMW_DCDC_GEN3.qea and in the C code (commit 39db4e93a, analyzed with archrev 0.1.0). Read-only: nothing was written back to the model.

How each side describes a module

UML model (.qea)

DCDC_Shared_Model/Component/MCU/Flex/APPL/<Module>/
  BlackBox/
    <Module>            Component («ASIL B» on safety modules)
      ProvidedInterface  one per exported function
      RequiredInterface  one per used signal / function
  Interfaces/
    <fn>  Interface «Function», 1 operation = signature
  type_defs/
    struct / enum / union classes (imported from a header)
  • The project view (100554_BMW_DCDC_GEN3/Static_View/Component_Diagram/MainController/Appl/<Module>) holds the component diagrams.
  • Features (Features/FUSA/…, Features/SEV/…) refer to modules as plain classes.
  • Required signals point to shared interfaces in SYSTEM/Signals, whose operations are SP_Get_/SP_Set_/SP_Test_<signal>.
  • Each module also has two copies under Playground/ImportWork and Playground/import_. They are ignored here.
  • Components and interfaces have no descriptive notes. A module's behavior is described only by diagrams.

C code

software/source/flex/appl/swc/
  <Module>.c   implementation + RTE runnables
  <Module>.h   public prototypes, macros, types
software/source/generated/Rte_<Module>*.h
  generated RTE ports (Rte_Read/Write/Call)
  • Provided = functions and globals with external linkage. Runnables (*_Main*, *_Init) are called by the RTE/OS, not by App code.
  • Required = everything the module calls, reads or writes outside itself: signal pool (SP_*), RTE ports, other SWCs, parameters (PAR_* in cds_data), drivers, BSW.
  • Extracted deterministically by archrev (libclang). Each dependency carries file:line evidence.

"Matching names": the same function name is a UML provided interface and an exported code function. A required interface counts as used when the code references its name, one of its operations, or an SP_*_<name> accessor. "Code calls not in UML" counts function calls and global reads/writes that no UML required interface names (macros and enum constants are not counted).

  • SEV matches its model completely. It is also the most recently maintained component (2026-03).
  • The required side of the model lists signals and RTE ports, but not direct C calls between modules, to drivers or to PAR_* parameters. Most real coupling (e.g. DCDC_FSM → DCDC_Control) is therefore not in the model.
  • DCDC_FSM has drifted the most: only half of its provided interface matches, its type_defs come from another project, and its state machine doesn't match the code states.
  • Naming: runnables are named differently in the model and the code (DCDC_Safety_Functions_Init vs DCDC_SF_Init). Any automated comparison needs an explicit name mapping instead of guessing.

UML holds a state machine under Dynamic_View/StateManagement (17 states; 104 trigger elements across two copies of the package). The code defines its states as DCDC_FSM_STATE_* macros in DCDC_FSM.h:40–57.

Method and limits

  • UML facts were read with SQL from the .qea (SQLite) tables t_object, t_operation, t_operationparams, t_attribute, t_diagramobjects and t_package. Only the DCDC_Shared_Model/Component/MCU/Flex/APPL component is compared. Playground copies are ignored.
  • Code facts come from archrev analyze outputs (model.json) for the release profile. Code disabled by the active defines is not seen.
  • Matching is by exact name, plus SP_*_<signal> accessors for signal interfaces. A signal reached through generic accessors such as SP_Get_Signal_Word(SignalID_x), or a DEM event reached through DemConf_* IDs, shows as "not referenced" even though it may be used.
  • "Not in code" for type_defs means the type name doesn't appear in the module's own .c/.h files.
  • The working tree had uncommitted deletions outside software/ (Cantata). They don't affect these modules.
